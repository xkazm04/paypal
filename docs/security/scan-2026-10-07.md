## 3. Risky code on the trust and internet-facing surfaces

The public service is one process:
- `house-seller` merges `rendezvous::router` into its own router (`services/house-seller/src/hosted.rs:596-603`).
- It shares one in-memory relay store (`services/house-seller/src/main.rs:17`) with the seller, which holds the
  HOUSE owner seed and the PayPal secret.

**Anything that crashes or stalls the relay takes HOUSE down too.** The comment at
`services/rendezvous/src/lib.rs:1` ("no signing keys or PayPal credentials") is true of the crate but not of
the deployed process.

### C-1 (High) - anyone can exhaust relay memory and crash the co-hosted HOUSE

- **Where:** the relay holds up to 256 mailboxes (`services/rendezvous/src/lib.rs:86`) × 256 messages each
  (`:117`) × 16 KiB per message (`:67`). That is about 1 GiB of strings on a `0.5c-512mb` instance
  (`render.yaml:8`). `PUT` and `POST` need no authentication. Expired boxes are swept only inside `create` (`:82`).
- **Scenario:**
  1. An anonymous caller sends about 128 `PUT /v1/mailbox/<random 64 hex>`.
  2. They then send about 32k `POST …/envelopes`, each with a different 16 KiB `a.b.<random base64url>` body.
     Because the bodies differ, the dedupe at `:114` never applies. In total this is roughly 512 MB of upload.
  3. The process is killed for running out of memory. HOUSE goes down mid-demo and every live mailbox is lost.

  The attack can be repeated after every restart.
- **Why it matters:** no money moves (deadline defaults still apply once HOUSE is back), but the one public
  surface judges use can be killed cheaply. This is a different problem from the known mailbox-*count*
  exhaustion folded into card relay-and-rendezvous-1. Authenticating `PUT` would shrink this attack too, but
  a byte budget takes a few lines and does not depend on that card.
- **Fix:**
  - Hold the store as `Mutex<Inner { boxes, total_bytes }>`.
  - Add `MAX_MAILBOX_BYTES = 256 * 1024` and `MAX_TOTAL_BYTES = 64 * 1024 * 1024`.
  - In `send`, return `Error::Full` (429) if either limit would be exceeded. Subtract a box's bytes when it expires.
  - Run the expiry `retain` in `send` as well, or from a 60 s `tokio::time::interval` task.

  The wallet already treats 429 as "retry later".

### C-2 (Medium) - the "resolved" PayPal binding evidence is not recorded on the live path, and the verifier claims checks it did not make

- **Where:**
  - `crates/table-paypal/src/client.rs:200-212` builds every `Observation.body` from
    `redact_paypal(&response.body, …)`.
  - The redaction allowlist (`crates/table-ledger/src/redaction.rs:10-33`) has no `custom_id`, `payee` or
    `merchant_id`, so those fields are dropped at this point.
  - `crates/table-app/src/pipeline.rs:400` passes that redacted body on as `PaypalCall.response`.
  - `crates/table-ledger/src/repositories.rs:819` and `:1462` then run `binding_projection` on it. As a result,
    `paypal_calls.binding_json` holds only `invoice_id` and the amount.
  - `crates/table-verify/src/lib.rs:309-336` checks each field only `if let Some(...)`, so a missing field passes.
    `:355` then prints the fixed claim "custom_id = terms hash, invoice, payee and amount match".
- **Why the tests miss it:**
  - `crates/table-ledger/src/tests.rs:679` feeds a raw body straight into `record_paypal_call`.
  - `crates/table-runtime/src/relay_tests.rs:1343-1357` goes through the real client but checks only the fixed
    text, and its tamper case changes only the amount.
- **Scenario:** a seller wallet creates an order through `Client::sandbox`. The ledger keeps only the invoice id
  and the amount. An exported proof bundle then states that the payee and the terms hash were verified, although
  they were never recorded or compared.
- **Why it matters:** STATUS § "Incidental sweep" lists this as resolved by the owner decision of 2026-10-06
  (`7d08e66`, migration 0007), but on the live path it does not work. The audit and proof evidence overstates
  what it proves, which matters for a submission whose signature is verifiable evidence. Money is still safe:
  `Order::verify` runs on the raw body before any money step.
- **Fix:**
  - In `Client::execute`, compute `table_ledger::binding_projection(&response.body, &secrets)` **before** redacting.
    Carry it as a new `Observation.binding` field, then as `PaypalCall.binding`.
  - In `record_paypal_call` and `finish_operation`, store `call.binding` instead of re-projecting the redacted body.
  - In `table-verify`, require `custom_id`, `invoice_id` and `payee_merchant_id` on every 2xx order call that has
    purchase units, and build the result text from the fields actually compared.
  - Add a test that runs a create through `Client::sandbox` with a mock transport and asserts that
    `paypal_bindings()` contains `custom_id` and `payee_merchant_id`.

### C-3 (Medium) - every HOUSE sale permanently holds one of 64 relay routes

- **Where:**
  - `crates/table-ledger/src/relay.rs:76-93` counts a route as live while its deal is not `terminal()`.
  - In `crates/table-core/src/deal.rs:122-135`, `Captured` and `Receipted` are not terminal. Only
    `ReportingMatched` moves a deal on to `Reconciled`, and the hosted seller never reconciles.
  - `hosted.rs:274` calls `bind_paired_relay` after four writes, each in its own transaction: the reservation
    (`:246`), the counterparty (`:249`), the deal (`:264`) and the category. It runs before the deadline is set
    (`:293`).
- **Scenario:** after 64 cumulative sandbox sales (rehearsals, video takes and judges), every new table gets
  `Conflict` from `bind_paired_relay` and the caller gets a 503. Each failed attempt also leaves behind a
  `Pairing` deal with a reservation and no deadline. That deal never defaults, and it holds one of the 64 HOUSE
  request slots (`hosted.rs:243`). The state lives on the persistent disk, and `docs/build/DEPLOY.md:100-105`
  forbids replacing the ledger, so HOUSE stays down.
- **Why it matters:** this is the same lockout as backlog §0 item 1 ("HOUSE locks out every judge after 64
  buyers"). That item was fixed for request reservations, but the lockout survives through the relay-route cap.
- **Fix:**
  - In `bind_relay`, count only routes whose deal is `state.pre_capture()`. A captured HOUSE deal has nothing
    left to relay except its receipt, which is sent before capacity matters.
  - In `Seller::table`, call `set_deadline` right after `create_deal`, and move `reserve_house_request` to the end.
    A failure then leaves nothing that holds capacity.
  - In `relay_work`, skip `Receipted` deals that have nothing owed.

### C-4 (Medium) - anonymous tables use up the daily deal limit and block deals already approved at PayPal

- **Where:**
  - `crates/table-ledger/src/repositories.rs:646` counts every deal created today under the mandate except
    refused, withdrawn, expired and voided ones. So `Pairing`, `Listed` and `Negotiating` deals count.
  - `crates/table-core/src/mandate.rs:385-388` refuses once `max_deals_day` is reached.
  - The check runs again before create, authorize and capture (`crates/table-app/src/pipeline.rs:263`) and before
    every approval poll (`services/house-seller/src/hosted.rs:528-531`).
  - `usage_for` excludes only the deal itself, so deals created *later* count against earlier ones.
- **Scenario:**
  1. A judge's HOUSE deal is `AwaitingApproval` or `Approved`.
  2. An attacker sends `max_deals_day` `POST /v1/house/tables` requests, each with a fresh self-signed Ed25519
     identity, which costs nothing.
  3. Every later check on the judge's deal refuses with "max_deals_day reached". The approval lapses, or the
     held authorization waits for the 72-hour auto-void.
  4. The attacker's `Listed` deals withdraw after 5 minutes, so repeating the requests every 5 minutes keeps
     HOUSE refusing.

  Ordinary traffic triggers the same thing once `max_deals_day` people open tables within one UTC day.
- **Why it matters:** the invariant holds (silence moves no money), but the demo can be broken on demand, and a
  buyer who has already approved on PayPal sees the seller refuse.
- **Fix:** in `usage_for`, add `AND id < ?2` (ULIDs sort by creation time) so later deals never count against
  earlier ones. Also exclude `PAIRING`, `LISTED` and `NEGOTIATING` from the count, so only agreed deals use the
  daily budget. The same change protects desktop wallets.

### C-5 (Medium) - approval polling every second writes two permanent rows per poll on HOUSE

- **Where:**
  - The HOUSE actor ticks every second (`services/house-seller/src/hosted.rs:581`) and polls each
    `AwaitingApproval` deal on every tick (`:531`), with no backoff.
  - Each poll records every PayPal observation (`crates/table-app/src/pipeline.rs:561-570`) as a `paypal_calls`
    row plus an append-only `audit_log` row (`crates/table-ledger/src/repositories.rs:1466-1476`).
- **Scenario:** anyone can negotiate to `Agreed` without a PayPal account (by accepting the house ask) and then
  never approve. Over the 6-hour approval window, one such order causes about 21,600 sandbox `GET` calls and about
  43,000 rows, and this repeats for up to `max_deals_day` orders every day. The effects (a rough estimate, not
  measured):
  - the 1 GB disk (`render.yaml:12-14`) fills during the judging window;
  - audit checkpoints re-verify an ever longer chain;
  - sandbox rate limits start to hit real deals.
- **Fix:**
  - Keep a per-deal `next_poll_at` in the actor, starting at 5 s and doubling up to 60 s. Reset it when the state
    changes.
  - Optionally, skip `record_paypal_call` when a `GET` returns the same status and body digest as the last
    recorded poll. Keep one audit row per status change, since that row is what proves the poll happened.

### C-6 (Medium) - no server timeouts, connection limit or long-poll limit

- **Where:**
  - `services/house-seller/src/main.rs:43` and `services/rendezvous/src/main.rs:17` use plain `axum::serve`. In the
    locked axum 0.8.9 the connection is built without a timer, so hyper's 30 s header-read default is inactive.
  - There is no request-body timeout and no idle timeout.
  - Nothing limits concurrent long-polls (`services/rendezvous/src/lib.rs:245`, `:302`), each of which can last up
    to 25 s.
- **Scenario:** thousands of idle keep-alive connections, request bodies trickled one byte at a time, or `wait=25`
  polls on the attacker's own mailbox. Each holds a socket and a task until file descriptors or memory run out.
  **PLAUSIBLE:** Render's edge proxy may buffer or time out some of this; I could not verify that here.
- **Fix:**
  - Add `tower_http::timeout::RequestBodyTimeoutLayer::new(Duration::from_secs(10))` and
    `tower_http::timeout::TimeoutLayer::new(Duration::from_secs(30))` to both routers. `tower-http` would be a new
    direct dependency; record it in STATUS.md.
  - Serve through `hyper_util::server::conn::auto::Builder` with
    `.http1().timer(TokioTimer::new()).header_read_timeout(Duration::from_secs(10))`, taking a permit from a
    `tokio::sync::Semaphore` (for example 512 permits) for each accepted connection.
  - Add a 128-permit semaphore for long-polls. When it is empty, answer at once as if `wait=0`.

### C-7 (Medium) - relay reads copy a whole mailbox under the one global lock

- **Where:** `services/rendezvous/src/lib.rs:140` and `:282` (`b.messages[offset..].to_vec()`) run under the
  store-wide `Mutex` (`:38`). The dedupe scan at `:114` also runs before the 256-message check at `:117`.
- **Scenario:**
  1. Fill one mailbox once (4 MiB).
  2. Loop `GET …/envelopes?after=0&wait=0` or `/sync`. Each request copies 4 MiB while holding the lock and then
     serialises roughly another 4 MiB of JSON.

  A few hundred requests per second saturate the 0.5 CPU, and HOUSE's own relay calls (`lib.rs:175-200`) queue
  behind the same lock.
- **Fix:**
  - Store messages as `Vec<Arc<str>>`, so a read clones pointers rather than strings.
  - Return at most 32 messages per response (`.iter().skip(offset).take(32).cloned().collect()`). The wallet already
    handles partial batches: `crates/table-runtime/src/relay.rs:177` advances by `after + messages.len()`.
  - Move the dedupe scan after the length check.

### C-8 (Low) - a stalled or dead HOUSE actor is invisible to the health check

- **Where:** `services/house-seller/src/hosted.rs:578-595` runs a single actor.
  - `tick()` awaits PayPal calls (30 s timeout × retries) while table requests queue in a 4-slot channel and then
    get 429 (`:565`).
  - `rx.await` (`:567`) has no timeout.
  - `tick` errors are discarded (`:590`).
  - A closed channel is reported as `Full` (429).
  - `/healthz` (`services/rendezvous/src/lib.rs:164`) answers 200 regardless.
- **Scenario:** if the actor task ever ends (for example, from a panic in a dependency), HOUSE answers 429 forever.
  Render sees a healthy service and never restarts it.
- **Fix:**
  - Wrap `rx.await` in `tokio::time::timeout(Duration::from_secs(20), …)` and map expiry to 503.
  - Map a closed channel (`TrySendError::Closed`) to `Error::Unavailable`.
  - Keep an `AtomicI64` heartbeat that the actor updates every tick, and make `/healthz` return 503 when it is more
    than 30 s old.

### C-9 (Low) - a hostile relay can grow the wallet's inbox and audit log

- **Where:**
  - `crates/table-ledger/src/relay.rs:180` accepts a new generation whenever `after == 0`.
  - `:183-192` inserts up to 256 × 16 KiB messages per batch.
  - Rows in `relay_inbox` are never deleted.
  - `finish_inbox` (`:252-262`) appends one audit row per rejected message.
- **Scenario:** a compromised or malicious relay (the design treats the relay as untrusted) answers every poll with
  a fresh 32-hex generation and 256 junk messages. That adds up to 4 MiB of inbox rows and 256 append-only audit
  rows per poll, for each live deal. Signatures still stop every message from being applied, so the only effect is
  disk growth.
- **Fix:**
  - Add `generation_at` to `relay_routes` and return `Conflict` for a second reset within 10 minutes; `Conflict`
    already triggers the backoff.
  - Cap `relay_inbox` at 1024 rows per deal.
  - Write one `envelope.rejected` audit row per batch, holding the count and the message hashes.
- **Status:** partly fixed.
  - The reset rate limit: a3d9a92 (2026-10-10), corrected in 2044b21 so that the window counts from the last reset.
  - The inbox cap: a3d9a92, 1024 rows per deal, plus pruning of settled rows of other generations on an accepted reset.
  - One `envelope.rejected` audit row per batch: fixed on the wallet (f870297, 6f7beb3). The HOUSE side is open, as C-9c.
  - See DECISIONS.md section 33.

### C-10 (Low, PLAUSIBLE) - the approval link from a counterparty is not bound to the order it claims

- **Where:**
  - `crates/table-proto/src/settlement.rs:23-36` (`approval_url`) checks only the scheme, the exact sandbox host,
    user info, port and fragment. Any path and query on `www.sandbox.paypal.com` passes.
  - `validate_settle` (`:37-61`) checks amount, invoice and intent, but not that `approve_url` refers to the SETTLE
    `order_id`.
- **Scenario:**
  1. A malicious peer wallet (not HOUSE) sends a SETTLE with the agreed amount and a real `order_id`, but its
     `approve_url` points at a different, larger order. Worse (unverified): it could point at another PayPal page
     on the same host that pays the peer directly.
  2. The owner opens it from the approval window, which presents it as the verified PayPal link.
  3. The only remaining safeguard is the owner reading the amount and payee on PayPal's own page.
- **Why it matters:** counterparty input is untrusted (AGENTS.md). The owner's click remains the authority, so the
  money invariant holds, but the wallet's "verified" framing makes the owner less likely to check.
- **Fix:**
  - In `validate_settle`, require the approval path PayPal returns for Orders v2 and a `token` query value equal
    to the SETTLE `order_id`. Reject any other path and any extra query keys.
  - `.research/paypal-platform.md` does not document the link format. Mark the check `// UNVERIFIED:` and list it
    in STATUS.md until a sandbox spike records a real `approve` link.

### C-11 (Low) - agent keys are silently re-minted on an existing wallet

- **Where:** `crates/table-runtime/src/service.rs:97-104` calls `signing_key` (which creates a key when it is
  missing) for the Negotiator, Shopper and Assistant slots, even when the ledger is not fresh. The owner key was
  fixed to fail closed (`:91-96`); the agent keys were not.
- **Scenario:** after a lost keyring entry, an agent quietly gets a new identity. Pinned counterparties and
  mandates bound to the old agent key then refuse it. They fail closed, so deals lapse with no clear cause.
- **Fix:** when `!ledger.is_fresh()`, use `existing_signing_key` for the agent slots too. Report a missing slot key
  as `Unavailable` with a fixed message.
- **Status:** closed. Part one fixed in 63e3627 (2026-10-10): it closes the silent re-mint on a wallet with history: the Negotiator slot is read with `existing_signing_key` and a missing key fails closed as `Unavailable` ("Agent key provisioning failed") with no key written; a Shopper or Assistant slot fails closed the same way when an active mandate pins an agent key that no present slot holds, and a never-used slot is still minted. A fresh ledger mints as before. **Closed in e91e859 (2026-10-10).** `Ledger::mandate_agent_keys` (read-only, no schema change) returns every agent public key any mandate row ever bound, whatever its status, and `provision_agent_keys` uses it instead of `list_mandates`. A Shopper or Assistant key bound only by a revoked, superseded or expired mandate now fails closed as `Unavailable` ("Agent key provisioning failed") with no key written; a slot no mandate ever bound is still minted, and a fresh ledger mints as before. The Negotiator is treated as used on any wallet that is not fresh.

### C-12 (Low, PLAUSIBLE) - keyring entries are readable by any process running as the same user

- **Where:**
  - `crates/table-runtime/src/vault.rs:71` and `:88` store Windows generic credentials under the service
    `TheTable.AgenticWallet` (owner key, agent keys, PayPal sandbox pair, Channel3 key).
  - Generic credentials can be read by any process of the same user via `CredReadW`.
  - On a fresh ledger, `signing_key` (`crates/table-runtime/src/service.rs:91-93`) adopts an `owner` entry that
    already exists.
- **Scenario:** an engine CLI, or a tool it runs as the user, reads the owner signing key and the PayPal client
  secret. A process that writes the entry before first run gets its own key adopted as the owner key.
- **Why it matters:** the design (§9) says the LLM can never see a client secret or a signing key. That now rests
  entirely on engine isolation, which this scan did not cover (`crates/table-engine/` was skipped).
- **Fix:**
  - Add a conformance test in the engine crate proving that a spawned engine child cannot call `CredReadW` for
    `*.TheTable.AgenticWallet`. For example, launch engines under a restricted token or in an AppContainer, or
    deny them shell tools.
  - On a fresh ledger, refuse to adopt a pre-existing `owner` entry: delete it and mint a new key, or ask the owner
    in the approval window.
- **Status (2026-10-10, addendum A6; still PLAUSIBLE, narrowed):** the engine surface is now read. No engine child can
  run at all today: `NativeEngine::probe` always returns `available: false` (`native.rs:450-455`) and
  `start_agent` refuses an unavailable engine (`engines.rs:156-158`). For claude-code the argv leaves no built-in
  tool (`--tools ""`, `argv.rs:21-22`), `Bash`, `WebFetch` and `WebSearch` are also denied (`:97`), and only
  `mcp__wallet__*` is allowed, so no tool exists through which a model could call `CredReadW`. For codex-cli the shell is
  off (`argv.rs:57`) but the sandbox is `read-only`, which restricts writes, not reads, and its other built-in tools
  are not enumerated (C-18); codex also cannot pass the init check, so it cannot start. What stays open: the fence is
  advisory by the research's own note (`.research/landscape-and-stack.md:21`), it has never been run live, and the
  child still runs as the same user with the CLI's own code. This closes only when a live conformance spike shows an
  engine child cannot read `*.TheTable.AgenticWallet` or the ledger. The fresh-ledger `owner` adoption half is
  unchanged and still open.

### C-13 (Low) - PayPal secrets are not zeroized, and the Authorization header is not marked sensitive

- **Where:**

  - `crates/table-paypal/src/client.rs:93` and `:133` return the access token as a plain `String`.
  - `:96` and `:104` build the Basic value with `format!`.
  - `:127-132` keep the id, the secret, the Basic value and the token for the client's lifetime.

  - In `ReqwestTransport`, build each header as a `reqwest::header::HeaderValue` and call `set_sensitive(true)`

- **Status:** closed by fix(paypal): zeroize secrets and mark the Authorization header sensitive (C-13) (1cc991e, 2026-10-10).

### C-15 (Info) - internal database and JSON error text reaches the webview

### C-16 (Info) - webview hardening

### Part A - engine and agent isolation

**A1 Environment - checked and sound, one note.**
`native.rs:57-83` calls `env_clear()` (`:61`) and re-adds `SYSTEMROOT`, `WINDIR`, `PATH`, `PATHEXT`, `TEMP`, `TMP`,
`USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `HOME`, `CODEX_HOME` (`:63-75`). All eleven are paths or lookup lists, so
none carries a value the wallet, the owner key or PayPal set. A secret in one of them would have to be put
there by the user. The wallet's own secrets are never in the process environment: they live in the keychain. The
test `inherited_canary_environment_is_stripped_before_child_launch` (`crates/table-engine/tests/native.rs:75`) seeds
canaries and checks they are gone. `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` and the `CLAUDE_CODE_*` controls are
dropped by `env_clear`; `STRIP_ENV` (`argv.rs:135-148`) is the documented list.
The only secret-like values the child receives are the run's own `WALLET_MCP_TOKEN` and `WALLET_MCP_SECRET`
(`native.rs:165-167`), by design. The child's profile paths (`USERPROFILE`, `APPDATA`, `CODEX_HOME`) let the CLI find its
own sign-in files, which is intended ("Subscription auth remains CLI-owned", `:81`); that is the same-user class of C-12.
Handles: the child gets stdin, stdout and stderr (`native.rs:154-156`). The workspace creates no inheritable handle
(no `bInheritHandle`, `set_inheritable` or `SECURITY_ATTRIBUTES` anywhere in `crates/`, `apps/`, `services/`), and Rust's
standard library opens files and sockets non-inheritable, so nothing else is inherited. I did not prove this for handles
inside third-party crates at run time.

**A2 Tool fence - checked, two findings (C-17, C-18).**

  directories above the cwd (`apps/desktop/src-tauri/src/native.rs:216`, `:231`), and the sibling run directories are one above.

**A3 Loopback MCP - checked, one Info (C-20), the rest sound.**
- **Bind and Host.** `Server::bind` binds `127.0.0.1:0` (`lib.rs:177-179`). `handle` requires `Host` to equal `127.0.0.1:<port>`
  and rejects any `Origin` header (`:300-304`), which blocks DNS rebinding and browser calls.
- **Secret.** `X-Wallet-Secret` must equal the server secret (256 bits from `getrandom`, `:81-85`, `:105`) at `:305`. The comparison
  is `!=` on strings, not constant-time. On loopback, with a 256-bit secret and an attacker who must already run code on
  the machine, a timing attack is not realistic; this is C-20 (Info). The secret is one value per process; the token is per run.
- **Tokens.** Each `issue` makes a 256-bit token, drops expired sessions, refuses beyond 64 and sets a fixed 120 s expiry
  (`:121-150`). `grant_for_run` is not enabled until the host sees the engine's init, `enable` needs the secret (`:151-164`),
  and `revoke` removes the session (`:165-169`). Calls check expiry again (`:325`). A call with `enabled == false` is refused as
  `SessionNotEnabled` and audited (`:357-359`).
- **Catalogs and money.** `catalog` (`:206-218`) is: Negotiator `table_view`, `market_reference`, `send_offer`,
  `accept_offer`, `withdraw_offer`; Shopper `market_reference`, `propose_purchase`; Assistant `book_query`. A name outside the role's
  list is `ToolAbsent` before decode (`:368-370`). No tool creates, approves, authorizes, captures, voids or refunds at
  PayPal: the offer tools sign a message ("Moves no money", `:229-237`), `propose_purchase` "waits for the owner"
  (`:238-240`), and `crates/table-app/src/agent.rs:657` records "no path here calls PayPal". Every intent passes through
  `agent_gate`, which checks pause, run liveness, role and category, the signer and `check_mandate` before delegating
  (`crates/table-runtime/src/engines.rs:362-383`), and the wallet checks again before any write (`agent.rs:418`).
- **Counterparty strings.** Results are structured data. `AgentProjection` holds typed fields only (`TableCounterparty` is an enum, `item_ref` a
  restricted id, `crates/table-core/src/agent.rs:164-191`; the runtime comment at `engines.rs:194-196` records that no NOTE

**A4 Grant lifecycle - checked and sound, one availability finding (C-19).**
`start_agent` issues one grant per run with the run's role and category scope (`engines.rs:172-190`, `:230`), so one run
never holds another's. The grant is revoked in `ActiveRun::drop` (`:20-31`), which also cancels the engine and aborts the task. `ActiveRun`
is dropped by `finish_run` (`:389`), which runs on the engine's own end (`actor.rs:468`: clean, error, timeout or cancel
all arrive as `EngineFinished`), on an event fault (`actor.rs:467`), on `cancel_runs` (`engines.rs:407`; dispatcher
`:617`, `:625`; actor shutdown `actor.rs:554`) and when the runtime is dropped. A grant cannot outlive its run:
the token expires 120 s after issue (`lib.rs:143`), the engine's total limit is 120 s
(`native.rs:25-26`), and the run's own `expires` is 120 s (`engines.rs:213`, `:368`). Crash: sessions are in memory, so a process
death drops them; the job object kills the child (A5). The gap is C-19: a run task that ends without sending
`EngineFinished` (a panic or an abort) keeps its `ActiveRun`, and the slot is not freed.

**A5 Process lifecycle - checked and sound.**
- **Job object.** The child is created `CREATE_SUSPENDED` (`native.rs:169`), put in a job with
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and no breakaway flag (`windows_job.rs:49-58`), and resumed only after assignment
  (`:63-86`). A failed attach drops the job (kills the child) or kills the child (`native.rs:172-178`). Dropping the job kills
  every descendant (`native.rs:243-244`), also when the app exits. `cancel` sets a watch flag that wins the `select!`
  (`native.rs:239-242`, `:500-506`). `cancellation_kills_descendants_and_dropped_runs_remove_registration`

- **Output caps.** `read_lines` caps one line at 64 KiB (`native.rs:311`), the whole stream at 4 MiB (`:295`), reads 4 KiB blocks

  and thrown away without keeping a byte (`native.rs:183-191`). `structured` text is capped at 64 KiB (`:482`). The version
  probe reads at most 1025 bytes under a 5 s timeout (`:418-427`). Time: 10 s to init, 120 s total (`:25-26`, `:197-203`, `:241`).
  Nothing unbounded.
- **Stream gate.** The parser refuses any event before an attested tool inventory (`parser.rs:83-85`), any tool not named
  `mcp__wallet__*` or not in the closed list (`:13-16`, `:63-76`, `:130-132`, `:171-173`), and any second init or unknown item
  type (`:52-54`, `:183`). An engine error text (`ErrorReported.text`, up to 64 KiB) is dropped by `engine_event` (`engines.rs:328`).

### New findings

#### C-17 (Low, PLAUSIBLE) - ambient instruction files can reach a claude-code agent

- **Where:** `argv.rs:95-126` (no `--safe-mode`; only `--setting-sources project`); `native.rs:63-79` (`USERPROFILE`, `HOME` kept);
  `native.rs:120`, `:153` (cwd under `<app data>/agents/<uuid>/cwd`).
- **Scenario:** the research says only `--bare` and `--safe-mode` skip `CLAUDE.md` and auto-memory (`.research/landscape-and-stack.md:177`),
  and `--setting-sources` does not. Claude Code reads `CLAUDE.md` from the user's profile and from the cwd's ancestors. A `CLAUDE.md` in the owner's profile or in a parent
  of the app data directory would be added to the negotiator's context. This is the owner's own text, not the counterparty's, so it
  cannot reach the agent from outside; it can change behaviour in ways the signed mandate does not describe, and a file left by another program could do the same.
- **Why it matters:** the invariants make the mandate the only authority. The wallet still enforces it (A3), so the agent cannot exceed it; the risk is an agent that follows unrelated instructions inside it.
- **Fix:** run the spike the research already lists (`.research/...:407`) on `--safe-mode`, pin the result in `argv` with a test on the argv
  vector, and root the run directory outside the profile tree (see C-18).

#### C-18 (Low, PLAUSIBLE, latent) - the codex-cli fence is advisory, and the run root sits beside the ledger

- **Where:** `argv.rs:47-60` (`--sandbox read-only`, `features.shell_tool=false`); `native.rs:48`, `:153`;
  `apps/desktop/src-tauri/src/native.rs:216`, `:231` (`wallet.sqlite` and `agents/` share the app data directory).
- **Scenario:** a `read-only` sandbox denies writes, not reads. If codex-cli keeps a built-in that reads a path (for example an image
  or file viewer, or another exec tool) after `shell_tool` is off, an agent could read `../../wallet.sqlite` (its path is two directories above the cwd), or
  another run's `mcp.json`. I could not enumerate codex's built-in tools: no source for them is in `.research/`, and no engine was spawned.
- **Why it matters:** the ledger holds the book and the deal history, not the signing keys (those are in the keychain). It would be a disclosure, not a money path.
  It is latent: codex has no `system/init` event, so the parser refuses its stream (`parser.rs:83-85`), and `probe` marks it unavailable.
- **Fix:** put the engine root outside the app data directory (for example under the temp directory, canonicalised, with the same `RunDirectory` guard), so no ledger lies on the cwd's path;
  keep codex unavailable until a tool inventory is attested; add a conformance test that a spawned engine cannot read a canary file outside its run directory (the same spike as C-12).

#### C-19 (Low) - a run whose task dies without `EngineFinished` keeps its slot

- **Where:** `engines.rs:249-293` (the task is spawned and its `JoinHandle` stored, never awaited or watched); `engines.rs:384-406`; `actor.rs:468`.
- **Scenario:** if the engine task ends without sending `EngineFinished` (a panic in the engine code, or the channel to the actor closing), the `ActiveRun` stays in `runs`: the 4-run limit and the one-run-per-deal check
  (`engines.rs:146`) refuse new runs until the next full cancel or restart. `agent_gate` refuses the stale run's calls once `expires` passes (`:368`), and the grant
  itself expires at 120 s, so no authority outlives the run.
- **Why it matters:** an availability loss that silences agents, not a money or secret path.
- **Fix:** have the actor poll `task.is_finished()` for runs past `expires` and call `finish_run(run, Failed)`.

#### C-20 (Info) - loopback MCP hygiene

- **Where:** `table-mcp/src/lib.rs:305` (plain `!=` on the secret); `:295-307` (the JSON body is parsed before Host and secret are checked);
  `:133` (expired sessions are removed only when a new grant is issued).
- **Why it matters:** none is exploitable by anything short of local code execution (A3). A local process can make the server parse up to 64 KiB per request without credentials.
- **Fix:** compare with a constant-time equality; take the body as `Bytes` and parse after the checks; sweep sessions on a timer.

#### C-21 (Info) - small leftovers

- **Where:** `pipeline.rs:122`, `rescue.rs:773-780`, `resolve.rs:122-129`: `parked_read` gets one entry per parked request id and is never pruned (a few bytes per parked operation, until restart).
  `native.rs:361-387`: a hard kill leaves `agents/<uuid>/` behind, and nothing sweeps it on start. Files hold placeholders and the fixed prompt, not a secret.
- **Fix:** remove the entry when its operation closes; delete `agents/*` at `attach_native_engines`.
