## Answers to the five questions

### 1. Can a joiner reach a deal with an unpaired, revoked or expired counterparty, or with an already-known or replayed deal id?

**No, through any entry point.** The detail:

- **One entry point.**
  - `Action::Join` is built only by the Tauri command `deal_join` (`commands.rs:384-391`).
  - It is served only by the `deal_join` arm (`dispatcher.rs:688`).
  - `join_deal` (`service.rs:788`) is its only caller. `create_deal_id` is otherwise reached only by
    `create_deal`, with a fresh `Ulid::new()` (`service.rs:782`), and by tests.
  - The authority row is `deal_join: APPROVAL, Owner, PRIVILEGED` (`table-client/src/authority_table.rs:241`).
    So it is the approval window, with the IPC token, unlocked. It is admitted at `dispatcher.rs:290`
    before anything runs.
  - No agent tool, MCP tool or HOUSE path builds a join.
- **The pin.**
  - `join_deal` refuses unless `counterparty_policy_at(key, now)` says paired with a live pin
    (`service.rs:793-800`). That means a confirmed pin that is neither revoked nor expired
    (`table-ledger/src/pin.rs:119-125`).
  - A second line, independent of `join_deal`: clause 2 (counterparties) must be present in every
    mandate (`table-core/src/mandate.rs:366-370`). Every rule a buyer can use (`Pinned`, `Paired`, `House`) requires `paired`
    (`table-core/src/mandate.rs:497-510`). `create_deal_id` runs that check (`service.rs:892`).
  - Before J-1, a **house** counterparty skipped the `join_deal` check. A revoked or expired house
    pin was then held back by clause 2 alone. It was still refused, as `Refused`, not `Invalid`.
- **The deal id.**
  - `join_deal` refuses any id that `get_deal` finds (`service.rs:801-804`). Since J-1 this applies
    to the house too. Before J-1, a second house join reached the `INSERT` and came back as
    `LedgerTrust: UNIQUE constraint failed: deals.id`.
  - Behind that, `deals.id` is the primary key (`table-ledger/migrations/0001_table.sql:16`).
- **Case and encoding variants of the ULID.**
  - The id crosses IPC as a typed `DealId`, a `u128`, not a string. `DealJoinArgs` is
    `deny_unknown_fields`.
  - The ulid crate decodes Crockford base32 case-insensitively, so `01arz…` and `01ARZ…` are the
    same `u128`. The ledger stores and looks up the canonical uppercase `to_string()`.
  - So no spelling of a known id is a new id. The client also refuses anything but the canonical
    uppercase form (`listingCode.ts:15`, `:52`).
- **Two joins racing.** The runtime is one actor: `execute` takes `&mut self`, and the Tauri side
  only sends to `state.actor`. So the pin check, the id check and the `INSERT` of one join cannot
  interleave with another join. The primary key would stop a second insert anyway.
- **TOCTOU after the join.**
  - A pin revoked or expired after the join stops the deal at the next inbound envelope:
    `preview_inbound` calls `require_live` for every message (`table-ledger/src/repositories.rs:917-926`).
  - Every later mandate check re-reads `counterparty_policy_at` (`table-app/src/agent.rs:381-383`).
  - The deal then withdraws at its Band deadline. A haggle mandate must have a Band
    (`table-core/src/mandate.rs:645-653`), so a joined deal always has a deadline (`service.rs:919-946`).
- **A replayed or foreign listing code.**
  - The buyer's mailbox is `H(pair code_hash ‖ deal id)` (`table-ledger/src/relay.rs:90-106`). The
    code alone does not reveal it.
  - The LISTING must verify under the pinned counterparty's agent key, for this deal id and this
    buyer's agent as audience (`repositories.rs:927-947`).
  - So a code for a table the seller opened with someone else never hears a listing, and lapses on
    silence.

### 2. Can a crafted listing code change the ask, item, delivery, payee or currency, carry oversized or malformed fields, or differ from what the owner is shown?

**What the code controls.** The code is not authenticated; its CRC-32 catches typos only (DECISIONS
§49). So a crafted code can carry any item, quantity, ask, currency and category. The owner sees them,
and Rust then binds them as follows:

- **Ask, item, delivery and currency (the ask is a `Money`, so it carries the currency).** They must
  equal the seller's signed LISTING, or the buyer stays at `Pairing` and lapses
  (`table-app/src/agent.rs:285-295`).
- **The buyer's own signed rules still bound everything.** Each check runs against the code's
  terms (`service.rs:892`):
  - the Band ceiling and its currency;
  - the per-deal limit and its categories;
  - velocity;
  - the human-present threshold.
- **Payee.** The code has no payee field. A buyer deal's payee is the counterparty's declared payee
  from pairing (`service.rs:837-841`).
- **Quantity and category are not in the LISTING** (J-3, J-4).
  - A quantity that differs from the seller's cannot close. ACCEPT carries the terms hash, and the
    receiving side requires it to equal both the pending offer and its own terms
    (`table-ledger/src/repositories.rs:1156-1159`).
  - Until then, the buyer's owner and agent negotiate on a quantity the seller never offered.
- **Oversized or malformed fields.** The decoder refuses them before anything is built
  (`listingCode.ts:40-56`):
  - exactly 9 parts;
  - an 8-hex checksum that matches;
  - a canonical ULID;
  - an item of `[A-Za-z0-9\-_.:@+]{1,128}`;
  - a quantity of 1-1000;
  - an ask of 1-15 digits, positive and a safe integer;
  - a currency and category from a closed list;
  - delivery `now` only.

  `Terms::amount` re-checks quantity, ask and currency in Rust. The one gap is that the whole pasted
  text has no length cap before the checksum (J-6, local only).
- **What the owner is shown is what is sent.**
  - `TableSheet.tsx` shows `decoded.table.terms.item_ref`, `qty × unit_price` and the category.
  - On the click, `go()` sends `codeJoinArgs(decoded.table, …)` from the same render's `decoded`
    (`tableDraft.ts:101-114`).
  - `codeJoinArgs` copies the terms and category through unchanged. Delivery is fixed to
    `digital_now`, the only one the code decodes.
  - The item alphabet is ASCII with no spaces, so there is no bidi or homoglyph trick on screen.

### 3. Does any join path move money, or advance toward authorize, without an owner decision or on silence?

**No.**
- `deal_join` is an owner act in the approval window (token, unlock).
- It creates a buyer deal at `Pairing` (`service.rs:827`), sets its deadline and binds its relay route.
  For a buyer it signs nothing and lists nothing (`service.rs:947-956`), and it makes no PayPal call.
  Every new test asserts that the HTTP mock saw no path.
- The deal leaves `Pairing` only on a verified LISTING that matches. Money moves only through the
  existing AUTHORIZE approval.
- Silence withdraws the deal at the Band deadline (`apply_deadline_default`, never a capture).

### 4. Is every join refusal and acceptance written to the audit log?

**Acceptance: yes. Refusals: now yes (J-2).**
- **Acceptance** writes `deal.created` (kind, mode, terms hash), `deadline.set` and, when bound,
  `relay.bound`, all in the ledger.
- **Refusals before the fix:** only refusals at the authority gate wrote `command.refused`. A join
  that Rust refused itself wrote nothing. That covers an unknown, unpaired, revoked or expired
  counterparty, a known deal id, a mandate refusal, or the wrong side or kind.
- **Since `c33c3df`:** each of those writes the same bounded row (command, window, tier; never the
  deal id, the terms or the token). A ledger that cannot answer (`Unavailable`) is not counted as a
  refusal.

### 5. Is the listing code ever logged or persisted with anything secret?

**No.**
- **Rust never sees the code**, only the decoded `DealJoinArgs`.
- **No logging:** `service.rs`, `dispatcher.rs`, `native.rs` `ask` and `commands.rs` log nothing on
  this path. The only `eprintln!` in `native/` is the notification fallback in `events.rs`.
- **Audit rows:** `deal.created` holds a terms hash. `command.refused` holds no arguments.
- **The client:**
  - Neither `listingCode.ts`, `tableDraft.ts` nor `TableSheet.tsx` uses `console`, `localStorage` or
    `sessionStorage`.
  - The pasted text lives in React state only.
  - The seller's code reaches the clipboard only on the owner's own Copy click.
- **The code holds no secret.** It is a deal id, terms and a category: no key, no mailbox and no
  pairing code.

## Fixed

### J-2 (Medium, fixed in `c33c3df`): a join refused past the gate left no audit row

- **Where:** the `deal_join` arm, `crates/table-runtime/src/dispatcher.rs:688-706`.
- **What:** `record_refusal` ran only for a refusal at the authority gate. Every refusal inside
  `join_deal` or `create_deal_id` returned an error with nothing in the audit log. That covers a
  stranger key, an unconfirmed, revoked or expired pin, a deal id already known (a replayed code),
  a mandate refusal, and the wrong side or kind.
- **Why it matters:** an owner or a reviewer could not see from the trail that a replayed or probing
  listing code had been tried. No money could move; the gap was in evidence.
- **The fix:** the arm now records one `command.refused` row for any error but `Unavailable`. It uses
  the existing rate cap (60 a minute; the overflow is counted in `refusals.unrecorded`).
  `LedgerTrust` is included, because an unknown key comes back as `LedgerTrust` (J-5).
- **Test:** `every_refused_join_is_in_the_audit_log_and_an_accepted_one_is_created`
  (`listing_code_tests.rs`). It covers:
  - a stranger, an unconfirmed pin and the seller side each add one row;
  - an accepted join adds `deal.created` and no refusal;
  - the same deal id again adds a row;
  - no row carries the deal id, the item or the token;
  - no PayPal path was called.

  It fails on the base (0 rows where 1 is expected).

### J-1 (Low, fixed in `af3874c`): the house skipped `join_deal`'s pin and deal-id checks

- **Where:** `crates/table-runtime/src/service.rs:784-806`.
- **What:** `join_deal` ran both checks only `if !house`, which left two gaps for a house:
  - **A revoked or expired house pin** was refused only by mandate clause 2, as `Refused`.
  - **A second join of the same house deal id** reached the `INSERT`. It came back to the approval
    window as `LedgerTrust: UNIQUE constraint failed: deals.id`: a ledger-trust error, with SQL in
    the message, for what is an ordinary refusal.

  This is not exploitable to reach a deal: clause 2 is mandatory, and the primary key held. It is
  defence in depth plus a wrong error class. The `Table` approval draft already required a live pin
  for the house (`configuration.rs:165-171`), so the two checks disagreed.
- **The fix:** both checks run for every counterparty. The house is then still checked against the
  table Rust kept (`service.rs:843-856`).
- **Test:** `deal_join_refuses_a_lapsed_house_pin_and_a_house_deal_id_already_joined`. It checks
  that a revoked and an expired house pin are `Invalid` with no deal, that a live house pin joins
  once, and that the second join is `Invalid`. Against the base it fails: the revoked case is
  `Refused` (clause 2), and the second join is `LedgerTrust`. The existing house tests still pass
  (42 tests matching `house`).

## Open

### J-3 (Low): the signed LISTING does not carry the quantity

- **Where:** `Body::Listing { item_ref, ask, delivery }` (`table-proto/src/envelope.rs:152-156`),
  compared in `receive_haggle` (`table-app/src/agent.rs:285-295`).
- **What:** the code's quantity is protected only by the CRC. A crafted or mistaken code with
  another quantity still reaches `Listed`, and the buyer's agent may negotiate.
  - The buyer's per-deal, velocity and human-present checks then run on the code's quantity, not
    the seller's.
  - It cannot close: an ACCEPT whose terms hash differs is refused on both sides
    (`repositories.rs:1156-1159`).
  - So no money moves, and the deal lapses on silence. DECISIONS §49 already notes that the
    altered-terms test leaves quantity out.
- **Recommended fix:** add `qty` to `Body::Listing`, set it in `list()`, and compare it in
  `receive_haggle`. This is a protocol change in `table-proto` and `table-app`, outside this scan's
  paths.

### J-4 (Info): the category is not bound to the seller

- **What:** the code's category is not in the LISTING. A crafted code picks the category the buyer's
  mandate check uses.
- **Why it is Info:** it can only pick among the categories the buyer's own per-deal clause allows,
  under the same limit, and the owner is shown it before joining.
- **Recommended fix:** none for the submission. Or carry the category in the LISTING along with J-3.

### J-5 (Info): an unknown counterparty key is a `LedgerTrust` error

- **Where:** `counterparty_policy` uses `query_row` with no `.optional()`
  (`table-ledger/src/repositories.rs:1082-1083`).
- **What:** a join naming a key never seen here fails as `LedgerTrust` ("Query returned no rows"),
  not as a refusal. It is refused and, since J-2, recorded. Only the error class is wrong.
- **Recommended fix:** map no-row to `LedgerError::NotFound` in `table-ledger`.

### J-6 (Info): no length cap on a pasted code

- **Where:** `decodeListingCode` (`listingCode.ts:40-48`).
- **What:** it strips whitespace, splits, and CRCs the first eight parts before it validates any
  field. So a very long paste is CRC'd in full. Only the owner's own paste in their own window is
  affected, and every field is length-checked after the CRC.
- **Recommended fix:** `if (text.length > 512) return { ok: false, why: 'malformed' }` at the top.
  Not made here, because the client tests cannot run in this worktree.

### J-7 (Info): join refusals share `command.refused` with gate refusals

- **What:** the J-2 row is the gate's row: command, window and tier. The trail cannot tell a
  wrong-window probe from a join that Rust refused, and both share the 60-a-minute cap.
- **Recommended fix:** if that distinction is wanted, add an action (for example `join.refused`
  with a `reason` code, never the arguments) to `table-ledger/src/audit_detail.rs`, outside these
  paths.
