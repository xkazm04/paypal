 03 · Position 
The spine: one Deal primitive, signed under one Mandate 
All six capabilities are the same object at different tables. A Deal always has two sides and a closed set of terms. An Open Mandate is the owner's signed limit on what their agent may agree to. A Closed Mandate is the wallet's countersignature on one deal, and the wallet only issues it if that deal fits. PayPal is the settlement rail, not the policy engine: PayPal has no per-agent budgets S·paypal-platform §6.3 .

 // crates/table-core/src/mandate.rs — AP2-inspired, implemented locally.
// PayPal documents no public AP2 API (paypal-platform §3.3, S). 
 pub struct OpenMandate { // signed by the OWNER key 
 id: MandateId, version: u32,
 agent_key: Ed25519Pub, // private half never leaves Rust 
 clauses: Vec<Clause>, // numbered; refusals cite them 
 not_before: Ts, expires: Ts,
 owner_sig: Sig, // over canonical JSON (JCS) 
}
 pub enum Clause {
 /*1*/ Roles(Vec<Role>), // Buy | Sell | Shop | Rescue 
 /*2*/ Counterparties(CpRule), // Pinned(keys) | Paired | House 
 /*3*/ PerDeal{ kind: DealKind, max_amount: Money,
 categories: Vec<Category> },
 /*4*/ Band{ item_refs: Vec<ItemRef>, floor: Option<Money>,
 ceiling: Option<Money>, max_rounds: u8, deadline: Ts },
 /*5*/ Velocity{ max_deals_day: u16, max_total_day: Money },
 /*6*/ HumanPresentOver(Money), // above: owner clicks 
 /*7*/ Payees(Vec<PayeeRef>), // firewall allowlist 
}
 pub struct ClosedMandate { // the wallet's countersignature 
 deal_id: DealId, open_mandate_hash: H256,

 decided_by: DecidedBy, // Policy(clause) | Human(at)

} 
 // crates/table-core/src/deal.rs — the one primitive 
 pub struct Deal {
 id: DealId, // ULID; label "D-0193" is display-only

}
 // A CLOSED set of fields. Nothing free-form reaches money. 
 pub struct Terms {
 item_ref: ItemRef, // own SKU | Channel3 product id

}
 pub enum Delivery { // decides WHEN the seller captures; 
 DigitalNow, // haggles are always intent AUTHORIZE

}

// "D-0193" is a per-install display label only, never sent. 
Why the deal's terms are a closed list: one published shop-keeping agent experiment ended up with its agent telling customers to pay a hallucinated account. Its second run approved a contract nobody had meant to offer, and the fixes reported were a hard margin rule, procedures and role separation S·landscape §1.8 . A closed list of deal types is the research note's own inference from those lessons (landscape §1.9 is marked [inference]), adopted here as a design choice A . Here, an offer is (item_ref, price, currency, delivery) and nothing else. The open/closed mandate split mirrors AP2 v0.2's open stage (constraints + agent public key, user-signed) and closed stage (bound to one transaction) S·landscape §1.3 . The mandate is committed to the counterparty as a hash, so your ceiling stays private but can be proven later, in the spirit of AP2's selective disclosure (SD-JWT) S·landscape §1.3 A: commitment scheme .

Each collision below is stated as a fact, followed by the smallest change that keeps the owner's intent. None of them is quietly designed around.

 Haggle "closes with a PayPal payment" No developer API lets one consumer send money to another. P2P exists only in the consumer UIs S·paypal-platform §0.1, §2 . The seller's wallet is a merchant : B's own REST app issues an Orders v2 order and A approves it as the buyer. Settlement is always Goods & Services, never Friends & Family S·paypal-platform §5 . One human approval per deal (the PayPal page). 
 "Each user is a merchant" Each user having a business account and REST app is a sandbox convenience. In live use, "You may not establish a PayPal business account primarily for personal… purposes" S·paypal-platform §5 . Two-user trading is a marketplace (AUP #18) or money-service (AUP #4) pattern that needs pre-approval S·paypal-platform §5 . The sandbox build is said to be a sandbox build. The pitch says "live use requires PayPal marketplace onboarding / MSB pre-approval" S·paypal-platform §6.12 . The wallet never holds funds in an app-owned balance S·paypal-platform §5 . A sentence in the video and README. 
 Subscription rescue No API lets a consumer list or cancel their automatic payments to other merchants S·paypal-platform §1.5 . Merchant-side : Maya rescues the shop's own subscribers. Every lever acts on one subscription (capture, suspend, revise) or sends one invoice; the plan-wide update-pricing-schemes is never used. The subscriber has no wallet, so the channel is PayPal's invoice email plus Maya's own email S·paypal-platform §1.4, §1.5, §7 . A consumer "rescue my subscriptions" story is out of scope.

 Spend firewall "budgets, allowlists, velocity" PayPal exposes no per-agent budgets, allowlists or velocity limits S·paypal-platform §6.3 . A vaulted wallet pays only the merchant that vaulted it S·paypal-platform §1.9 . Policy is the open mandate, checked in Rust before every create/authorize/capture.  06 · Machine · centerpiece 
The haggle protocol: two wallets at one table 
Two installs, two sandbox accounts, one agent each S·scope §3 . The agents exchange signed envelopes through a store-and-forward rendezvous that can't read keys, change terms or touch PayPal. Each agent can only name a number, and the Rust core signs it only if it falls inside that owner's band. Settlement is one order that B issues and A approves. 
The model may pick any number it likes. The wallet will only sign numbers inside the owner's band, and an unsigned offer doesn't exist. How limits bind each agent

6.2 The envelope 
 // crates/table-proto/src/envelope.rs
// Compact JWS, alg EdDSA (Ed25519). Modelled on signed-offer
// JWTs with an `aud` anti-replay claim (landscape §1.6, S). 
 pub struct Envelope {
 v: u8, // protocol version = 1 
 typ: MsgType,
 deal_id: DealId,
 seq: u32, // strictly +1 per sender 
 prev: H256, // hash of previous envelope (either side) 
 iss: KeyId, // sender agent key id 
 aud: KeyId, // receiver key id — anti-replay 
 iat: Ts, exp: Ts, // offers live ≤ 10 min 
 nonce: [u8; 16],
 body: Body, // closed enum below 
} // sig = Ed25519(agent_key, JCS(envelope)) 
 pub enum Body {
 Hello{ owner_key, agent_key, mandate_commitment: H256,
 owner_sig_over_commitment: Sig, display_name: Short32 },
 Listing{ item_ref, ask: Money, delivery: Delivery },
 Offer{ price: Money, delivery: Delivery },
 Counter{ price: Money, delivery: Delivery },
 Accept{ offer_seq: u32, terms_hash: H256 },
 Settle{ order_id, approve_url, amount: Money,
 invoice_id, intent: Intent, attempt: u8 },
 Approved{ order_id }, // A: "I clicked approve" 
 Receipt{ capture_id, amount: Money, status,
 transcript_head: H256 },
 Withdraw{ reason: ReasonCode }, // enum, not text 
 Note{ text: Short280 }, // HUMAN-ONLY; never shown to agents 
} 
 Type Sent by Rust check before sign / after receive 
 HELLO both key format; commitment signed by owner key 
 LISTING seller item_ref ∈ seller clause 4; ask ≥ floor 
 OFFER / COUNTER both price in band; round ≤ max_rounds; now < deadline; delivery ∈ allowed enum 
 ACCEPT both (2 sigs) accepted price is the counterparty's last signed price; terms_hash recomputed 
 SETTLE seller amount = terms; intent = AUTHORIZE; invoice_id = deal ULID + attempt; URL host allowlisted; attempt ≤ 3 
 APPROVED buyer only after the owner clicked "Open PayPal" for this deal 
 RECEIPT seller amount = terms; transcript_head equals ours 
 WITHDRAW both reason ∈ enum; legal in any pre-capture state 
 NOTE owners ≤ 280 chars; shown in a quarantine box to the human only 
On receipt, the core rejects any envelope with a bad signature, wrong aud , expired exp , a nonce already seen ( nonces_seen table), a seq gap or a prev mismatch. The rejection is audit-logged and the deal state doesn't change A . Both sides keep the same hash-linked envelope chain, so the transcript head is one hash either party can recompute and verify.

 fn send_offer(&self, d: &Deal, price: Money) -> Result<Envelope, Refusal> {
 let m = self.mandates.active_for(d)?; // clause 1, 2 
 m.band(d.item_ref())?.contains(price, d.side)?; // clause 4 
 m.rounds_left(d)?.at_least(1)?; // clause 4 
 m.before_deadline(now())?; // clause 4 
 self.velocity.check(&m, price)?; // clause 5 
 let env = Envelope::offer(d, price, self.next_seq(d));
 self.ledger.append_out(&env)?; // hash chain first 
 Ok(self.signer.sign_agent(&m.agent_key, env)) // key never in JS/LLM 
}

// plus clause 6 (HumanPresentOver) → queue a countersign card. 
A refusal comes back to the agent as an MCP isError naming the clause, for example "clause 4: price 352.00 above ceiling 340.00". The agent can try again, but only with a number inside the band. 
6.5 Settlement: a seller-issued order 
 1 · Both sign ACCEPT The deal is closed with two signatures. Clause 6 may require A's owner to click countersign. 
 2 · B creates the order POST /v2/checkout/orders with intent: AUTHORIZE from B's own REST app (B is the merchant). The amount is exactly the deal amount S·paypal-platform §1.1, §2 
 3 · Link in a signed SETTLE The approve link ( rel: payer-action S·landscape §3.5 ) travels to A inside B's signed envelope. 
 4 · A approves A's wallet checks the link against the signed deal, then opens it in the system browser S·landscape §3.5 . The owner approves as buyer. 
 5 · B authorizes, captures, signs B polls GET /v2/checkout/orders/{id} until APPROVED, calls …/{id}/authorize , then /v2/payments/authorizations/{id}/capture on delivery, and sends a RECEIPT with the capture id S·paypal-platform §1.1, §1.2, §4 . Receiving money on an order A already approved needs no click (H5): B's authorize and capture on its mandate pass a shield ASK, while HOLD or BLOCK stops them. 
 Always AUTHORIZE , as the research recommends. The note's framing for haggling is "an AUTHORIZE order or invoice that B issues and A's human approves" S·paypal-platform §2 . Round 1 used CAPTURE for digital goods; that is withdrawn. The Delivery enum now decides only when B captures: DigitalNow straight after authorize, ShipThenCapture inside the 3-day honor period S·paypal-platform §1.2 . Until capture, a hold exists and B can void it if the deal falls through. Calling /orders/{id}/capture on an AUTHORIZE order returns 422 ACTION_DOES_NOT_MATCH_INTENT S·paypal-platform §1.1 . 
 invoice_id = {deal ULID}-{attempt} , never the display label. PayPal treats invoice_id as unique per merchant and rejects duplicates with DUPLICATE_INVOICE_ID S·paypal-platform §1.1 , so B can't settle the same deal twice. The house seller is one merchant shared by every judge, so a per-install label like "D-0193" would collide across installs; a ULID can't A . The attempt suffix exists because an expired order may still hold its invoice_id A: unverified, spike . 
 The deal hash travels with the order. custom_id = first 32 hex characters of terms_hash and description = "Deal 01JD…7Q · monitor-27-4k". The field semantics and length limits are R and must be checked against the spec on day 1. 
 The approval window is shown as a countdown. The link has 6 hours by default S·paypal-platform §1.1 . If it expires, B re-issues the order with attempt+1 (at most 3). 
 Never Friends & Family. Goods and services must be paid as a commercial transaction S·paypal-platform §5 . The scam shield flags any NOTE asking for "personal" payment as the User Agreement's "Buyer Scam" typology S·paypal-platform §5 .

Architecture 
Your desktop holds everything that can sign or spend. Render holds two small things: a mailbox that only forwards signed envelopes, and a scripted house seller. PayPal is reached only from Rust, and Channel3 only from Rust. The engine CLI is a fenced child process whose sole tool surface is the wallet's local MCP server. 
 Components and where they run top: your desktop · bottom: the peer, hosted pieces, PayPal, Channel3 
The stack follows the owner's existing app: Tauri 2 + React + Rust, axum for the local server, rusqlite, the keyring crate, AES-GCM S·owner-assets §5, §4 . Pin Tauri v2.12.x and plugins 2.x , because v3 alphas are already published S·landscape §3.0 . 5 · Against the other shortlisted variant (A-1 Checkpoint): why build The Table 
The Table keeps A-1's guarantee A mandate clause is a gate rule. A request outside the mandate is refused before any PayPal call, with the clause named and zero rows in paypal_calls (test F1), which is exactly A-1's Deny path. The approval lives in a separate window label, as in A-1 (#c1). Choosing The Table loses none of A-1's safety. 
…and adds the counterparty Three of the six capabilities have someone on the other side (haggle, shop, rescue). In A-1 they are sources of intents feeding one lane (#spine). Here the other side is on screen: who they are, whether they're paired, what the market says, and what they signed. That is the "practical business situation anyone can understand" the owner asked for: Maya buys a monitor from Dan for less than the market median, and both hold the proof. 
The prize bet is less contested "Best Use of Agentic Commerce" is agent-to-agent commerce, which is this report's literal subject. Channel3 is one $1,500 prize that few entries will call meaningfully A , and here it is load-bearing (the band). A-1 aims at AG Grid, the largest sponsor pot. Its own prize section flags a floor case of an HM plus an AG Grid runner-up (#prize). 
Where A-1 still has defects Its haggle settles on CAPTURE, where the research recommends AUTHORIZE or an invoice (#c9). Its GPU denial cites a "per-tx cap $25" (#top), yet a $38 purchase is described as within budget and held, not denied (#c1, #surfaces). Its video recovers revenue with an outstanding-balance capture after a replayed failure, which leaves no real balance to capture (#judges). None of these is fatal, and this report had two of the same kind in round 1. The difference is that they are fixed here.
